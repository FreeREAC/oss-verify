# Frequently asked questions

This page answers the questions that [theorem.dev/oss-verifier](https://theorem.dev/oss-verifier/) does not answer yet. It is for maintainers and for other readers.

## How do you choose projects?

<!-- draft: policy to review -->

**Enrollment.** We accept an established project that has a critical effect on the security of infrastructure and users. Our criteria are like those of OSS-Fuzz, and we decide case by case. We consider how much untrusted input the project gets, and how many users and dependent projects it has. A project must also obey these conditions:

1. The person who enrolls the project is a core maintainer of it.
2. The project has a licence that the Open Source Initiative approves.
3. The project has a public git repository, which we get anonymously over `https`. One project directory names one repository.
4. The project has at least one fuzz target: its own, its OSS-Fuzz fuzz targets, or new ones.
5. Our builder can build the project. The [language table](project-yaml.md#language) tells which languages it builds today.
6. The project has a security contact. We send each finding to this address.

Usually we do not accept a fork, a new project, or a project that nobody maintains. A person reviews each enrollment. The triage comment on the pull request helps the review: for example, it shows the licence, the activity and the criticality score of the project. If we decline a project, we tell you why in the pull request.

**Seeding.** We seeded the projects of OSS-Fuzz, at its commit `bd2ce21991a94a362b92fb1bf25f86d5a1a60842`, that our builder can build and that we can describe honestly. A seeded `project.yaml` gives only what the recorded build data tells, and no guess. [seeded-projects.tsv](seeded-projects.tsv) lists each of the 1,381 projects of OSS-Fuzz at that commit. For a project that we did not seed, it gives the reason. We publish a seeded project only while it has no findings. A core maintainer can adopt a seeded project ([project-yaml.md](project-yaml.md#seeded-projects)).

**Order of work.** We work first on the critical infrastructure that many other projects depend on. We are likely to verify a smaller project sooner. We measure its size in kilobytes of `.text` in its binaries.

## How do I enroll a project?

Follow the steps in the [README](../README.md#enroll-a-project). A coding agent can do most of the work with you. Tell it to read [AGENTS.md](../AGENTS.md). You open the pull request yourself.

## What do maintainers receive?

We send each finding to `primary_contact` and to each address in `auto_ccs`. A finding contains the input, the build and the binary, and the steps to reproduce it. It contains a patch when we have one. We also send each build problem to `primary_contact`. In `patch_style.md`, you tell us which findings, reports and patches you want ([project-yaml.md](project-yaml.md#patch_style)).

Findings and patches are generated by AI models, and they can be wrong or incomplete. We do not promise that a person reviews them before we send them. Review every patch before you use it. We follow your project's policy on AI-generated contributions.

We publish the statements and proofs about your project when the `publish` field tells us to ([what-gets-proven.md](what-gets-proven.md#publishing)).

## What is the disclosure policy?

There is no disclosure deadline, and we do not publish findings. You decide if and when a finding becomes public. [what-gets-proven.md](what-gets-proven.md#findings) gives each rule, also for seeded projects.

## Can I pause or leave?

Yes. The [README](../README.md#pause-or-leave) tells how.

## How do I send feedback?

To send feedback about a finding or a patch, reply to its report, or write to [oss-verifier@theorem.dev](mailto:oss-verifier@theorem.dev). If you have not enrolled a project, send your questions to the same address. To report a vulnerability in this repository or its tools, follow [SECURITY.md](../SECURITY.md).

## How does attribution work?

<!-- theorem.dev/oss-verifier gives the same answer. Remove this answer when that page is live (one home for each fact). -->
We do not require credit. If you fix a bug that OSS Verifier found, we ask for one line about it. Put the line in the commit message, or in the place where you give credits. Give the id from our report in it, for example:

    Found by Theorem's OSS Verifier, as finding THM-2026-7K3QF9XA.

The id helps us find which findings were real and which got fixed.

A finding id has these parts, in this order:

1. `THM-`;
2. the year in which we first report the finding, for example `2026`;
3. a hyphen, `-`;
4. 8 random characters from Crockford's base32 alphabet, in capitals. This alphabet has the digits 0 to 9, and the letters A to Z but not I, L, O and U.

As a regular expression, an id is `THM-[0-9]{4}-[0-9A-HJKMNP-TV-Z]{8}`. Each finding gets one id, when we first report it. We never use an id again. A duplicate of a finding keeps the id of that finding.

## How do you send reports only to the right people, and only about your code?

* Only a core maintainer can enroll a project. A person reviews each enrollment before we merge it.
* The triage comment shows whether the project's security policy, and its OSS-Fuzz project, give the address in `primary_contact`.
* We send findings only to `primary_contact` and `auto_ccs`. If you set `pgp`, we encrypt each report to your key and send it to `primary_contact` only.
* We send the findings of a seeded project to no one automatically.
* A statement is about the binaries that we build from your repository at a pinned commit, with the fuzz targets in `fuzz_targets`.

## How do you keep the data secure?

* We build your project from its public repository. The compile step has no network access.
* If you set `pgp`, we encrypt each report to your key.
* We do not publish findings. What we publish does not show a finding that is not public.

## Why static riscv64 programs?

The statements use a formal model of a riscv64 Linux process ([what-gets-proven.md](what-gets-proven.md#the-statements)). A statement is about each byte of the program. A static program holds all of its code: the library, the fuzz target, the driver and the C library. Thus no code from outside the binary runs.

## Which languages can you build?

The [language table](project-yaml.md#language) gives the status of each language. It also tells which languages the builder builds today.

## Why must two builds give the same bytes?

A statement is about the exact bytes of a binary, which the lock pins by their SHA-256. You can rebuild a binary and compare it with the lock only if each build gives the same bytes. Thus we pin only binaries that two clean builds reproduce. `tools/check --twice` makes this test, and the Build check of each pull request runs it ([build-contract.md](build-contract.md#reproducibility)).
