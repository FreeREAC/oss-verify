# Status (internal engineering status)

**Internal.** This page is the engineering status of the repository, for the people who build it. It is not documentation for maintainers. It moves out of the repository before the repository becomes public.

The repository is not open for enrollment yet. This page tells what works today, how we checked it, and what does not work yet.

## Works, and how it was checked

* **`tools/validate.py`** and the rules in [docs/project-yaml.md](docs/project-yaml.md): `python3 -m unittest discover -s tools/tests`.
* **The builder and `tools/check`**, on the cjson pilot: `tools/check --twice --lock <harness.yaml> cjson`, with the oss-fuzz-theorems 2026.10 release's `projects/cjson/cjson_read_fuzzer/harness.yaml`, builds all four binaries byte for byte as that release pins them, and a second build from scratch is identical:

  | build | bytes | sha256 |

  | plain | 72,792 | `b40ed189a37beb50da46f04a457ec144b05319a845fa3b0639d7a117ffd1696d` |
  | ubsan | 73,120 | `73d8f136684412bc2827dd90598b3b66fa023b78537ce674aa5007e9be78cbd0` |
  | asan | 606,648 | `09e0835df41a2bab7c8e4af1e6b990748fde19337e65f5b2993ae8be5e9d3a5f` |
  | asan-ubsan | 604,408 | `57f377d242bdd8fa074ec06428b9785e4d6357af953724e1c9a0533f271847d8` |

  The same holds for the md4c and wasm3 drafts (below), each against its `harness.yaml` in that release.
* **Builds ported from the oss-fuzz-theorems 2026.10 release** ([docs/build-contract.md](docs/build-contract.md#builds-ported-from-oss-fuzz-theorems)): `tools/verify_ports.py` ported the build of each of the 312 projects `tools/seed.py` can seed, and checked it with `tools/check --no-shell --lock` against the release's `harness.yaml` for every fuzz target in its `project.yaml`. **311 reproduce** the release's binaries: every binary of all four builds, 3,156 in all, byte for byte. numactl's among them runs autoreconf in its `build.sh` in place of the release's 1.2 MB patch of autoreconf's output, which a project directory cannot hold; in the toolchain image autoreconf writes exactly what the patch does. The one that does not, varnish, fails: its git server, code.vinyl-cache.org, serves only git's "dumb" HTTP protocol and fails to serve some of the objects of varnish's repository and of its VTest2 dependency, so neither commit can be fetched. GitHub's varnishcache/varnish-cache has varnish's commit, but no mirror of VTest2 has its. Most were checked with earlier versions of the builder. Its changes since (the allocation-failure engines, fetching by a full clone from a server that will not serve one commit, the release's path for a ported build's compiler, which only openssl records, and a toolchain chosen by the lock, the release's for every port) do not change what those projects compile and link; openssl, numactl and dnsmasq were checked again after the ones that concern them, and cjson, md4c and wasm3 after every one. [tools/seeds/builds.tsv](tools/seeds/builds.tsv) has the result for each project, and [docs/seeded-projects.tsv](docs/seeded-projects.tsv) repeats it. The builds that reproduce are C and C++ builds with CMake (167 projects), autotools (76), Meson (24), Makefiles, header-only libraries (22), and the release's direct compiles of a library's sources (37). `tools/check --twice` built h2o, hunspell, myanmar-tools, boost-beast and tink-cc from scratch a second time: identical.
* **The driver's exit statuses** ([docs/build-contract.md](docs/build-contract.md#the-driver)): `OV_DOCKER_TESTS=1 python3 -m unittest tools/tests/test_builder.py` builds a C and a C++ fuzz target with the templates' commands and runs all four builds of each under qemu-riscv64.
* **Allocation-failure fuzz targets** ([docs/build-contract.md](docs/build-contract.md#allocation-failure-fuzz-targets)): the same test builds the allocation-failure variants of its two fuzz targets, with the published engine, which ignores counting mode, and with the counting one, and checks the allocation mask, counting mode and `std::bad_alloc` in all four builds. It also builds cJSON's fuzz target with both engines (a test fixture): `cjson_read_fuzzer` keeps the release's four binaries, an input whose run makes 21 allocations has 21 counted in every build, and failing any one of them, or all, still exits with 0.
* **The workflows** in `.github/`: actionlint finds nothing, and the step that takes `projects/<name>/` from a pull request has been run against a local repository with good and bad pull requests.
* **The rebuild block** that `tools/check --twice` writes into the manifest: `tools/tests/test_check.py` runs `tools/check` with the builds replaced, for both results. A real `tools/check --twice cjson` wrote `result: identical`, with the release's four SHA-256s in both builds. The second build's image ids differed from the first's, and its toolchain did not.

## Not yet, or not checked

* **ubsan_checks**, in a provisional format (add, remove, reason) until its final format is agreed: `tools/validate.py` checks the names (clang 20's, probed in the toolchain image for riscv64 trap mode) and requires a reason. With today's toolchain (`fixed` in infra/toolchains.tsv), `tools/check` refuses the field. The builder's path for a list (OV_UBSAN_CHECKS) is tested with today's clang in tools/tests/test_builder.py, and used only once a toolchain row says `checks`. The trap-mode exceptions (vptr, function) are pending probes of the toolchain, and the skill's suggested removals are to come.
* **The next driver contract** (status 3 when a call returns -1; halts statements accept 0, 2 and 3) is documented as a note in docs/build-contract.md and the skill's step 3.7. The vendored driver does not change until the next toolchain version brings it; projects with proofs stay on today's driver.
* **docs/dsl.md** describes the format; its runtime is not in this repository yet, and the arming of the allocation mask in the new shape is pending.
* **DSL drivers** are not in this repository yet. When they come, they have the `LLVMFuzzerTestOneInput` shape (the skill's step 3.1 and 3.7, and docs/build-contract.md), and main carries only that shape. Proven API drivers keep their earlier whole-program shape until they are proved again: their locks name the recipe commit that builds them. The details of the operations are to come.
* **The toolchain image** that the builder is built `FROM` (`ghcr.io/theorem-labs/oss-fuzz-theorems-toolchain@sha256:6a6b4816…`) is not public yet. Until it is, `tools/check` and the Build workflow work only on a machine that already has it.
* **The builder image is not published.** `tools/check` builds it from `infra/base-builder/` and passes it to each Dockerfile as `BASE_BUILDER`; the Dockerfiles' default, `oss-verify-base-builder`, is that local name. Once it is pushed, that default should be its digest.
* **The workflows have not run on GitHub**: they are linted, not exercised there.
* **Hand-written build files:** a `build.sh` written for this builder by hand has been tried with CMake builds only (cjson, md4c, wasm3 and the test fixture). The ported builds use the release's recipes for the other build systems; the builder offers no Meson cross file or autotools settings of its own to a hand-written `build.sh` yet.
* **Allocation-failure fuzz targets** have no statement yet, and no project builds one.
* **Languages other than C and C++.** `tools/validate.py` accepts OSS-Fuzz's names (`rust`, `python`, `go`, `jvm`, `javascript`), with their source suffixes, and `sanitizers: []` as the default for `go` and `jvm`. infra/toolchains.tsv has a `languages` column, and `tools/check` builds a project FROM the newest toolchain for its language. The builder builds `rust`, `python` and `go` (below); `tools/check` refuses the others. R is pending and likely address-only: its UBSan build meets undefined behaviour inside R itself. `tools/validate.py` does not accept `r` yet.
* **Rust.** The builder builds a Rust fuzz target with the release's Rust recipe ([infra/base-builder/rust/](infra/base-builder/rust/)), FROM the release's Rust toolchain image. Its ubsan build is rustc's `-Zub-checks`; a panic exits 79 and an allocation failure 2. Checked locally with `tools/check --lock`, with the release's own names for the two Cargo packages that the recipe adds: bincode, and one fuzz target each of data-encoding (debug assertions), tokio (a second fuzz directory), image-png (git dependencies), lz4_flex (C dependencies through cc-rs) and harfrust (profile settings) make 28 of 28 binaries byte for byte as the release's Rust build did. Those names spell an internal name, so this repository names the packages `oft-rust-shim` and `oft-rust-rt`; cargo hashes the names into each crate's metadata, so every Rust binary here differs from the release's (measured on bincode: 8 of 8). On the build farm, `tools/check --twice` built all 31 Rust projects (82 fuzz targets, 328 binaries) twice from scratch with identical bytes; bincode's binaries there are also those of a build on this machine. An AddressSanitizer detection in a Rust binary takes about 160 s under qemu, where a C one takes seconds (measured on the Rust fixture of tools/tests/test_builder.py): this matters for the time of a proof, not for what it proves. zstd-safe first failed: its build needs the zstd submodule, which the release's build checked out (it checked out each tree's submodules). The ports of the projects whose repository has submodules (zstd-safe, mp4parse-rust and quick-xml, and the Python tinycss2 and tomlkit) now check them out too; the other four make the same bytes with them as without. tar-rs, toml_edit and two of h2's fuzz targets were not in the release's last Rust build; the release held back toml_edit's `asan` build (an AddressSanitizer report with LTO that is not in toml_edit).
* **Python.** The builder builds a Python fuzz target with the release's Python recipe ([infra/base-builder/python/](infra/base-builder/python/)), FROM the release's Python toolchain image. mdurl and idna (all 3 of its fuzz targets) make 16 of 16 binaries byte for byte as the release's Python build did, here and on the build farm; those are the only binaries of that build that we have. On the farm, `tools/check --twice` built all 31 Python projects (41 fuzz targets, 164 binaries) twice from scratch, with identical bytes. zipp first failed with no network: its build backend's plugin downloads a LICENSE file when the tree has none, so its port pins one, which no binary holds. The documentation of the Rust and Python exit statuses (79, a Rust panic or an uncaught Python exception; 80, a failed Python start; 2, also running out of memory) and of the runtimes' differences from OSS-Fuzz is drafted and waits for review, so docs/build-contract.md does not have it yet.
* **Go.** The builder builds a Go project with OSS-Fuzz's own `build.sh` and OSS-Fuzz's Go helpers, as the release did, in the release's Go toolchain image ([infra/base-builder/go/compile-go](infra/base-builder/go/compile-go)): the plain build only, with a patched Go runtime that the image holds, and the modules pinned by a `go.lock` (the `gomodules` line of `sources`). Checked locally with `tools/check --twice --lock` against the release's Go build: all 22 projects (38 fuzz targets) make each of their binaries byte for byte as the release's did, twice from scratch, here and on the build farm. gonids is not ported: its `Dockerfile` downloads a zip file that changes at its URL, no copy of the one that the release used is public, and the release pinned no binary for it. A Go fuzz target exits with 79 for a panic, 80 for a fatal error of the runtime, 139 for a load through a nil pointer (the runtime installs no signal handler), and 2 also after the system refused the runtime memory ([docs/build-contract.md](docs/build-contract.md#go-fuzz-targets), which also tells how the runtime differs from OSS-Fuzz's; its policy is marked as a draft). All Go binaries are over the size cap. go-coredns's binaries link modules under the MPL-2.0, whose source would have to be offered with them.
* **Lua, JavaScript and Ruby: not ported yet.** The release's builds of these languages are not in its release, and none of their binaries can be made again on this repository's toolchain: they were built on an older toolchain (another musl `libc.a`), with internal names in their bytes. The language table's statuses stand.
  * Lua (luzer harnesses): waits for the next toolchain version. The `lua` project's two Lua-script fuzz targets, string_rep_test and table_concat_test (lunapark, the same commit), build with the driver contract of that version (each call made, -1 is status 3, the allocation mask ignored), and two builds make the same bytes; the release has no Lua binary to compare with. The statements that we publish together all use one driver contract, and the project's two C fuzz targets keep today's driver and the release's bytes. So the Lua fuzz targets join the `lua` project when statement-only projects move to the next toolchain version; until then their recipe is not in this repository. lua-example is not ported: its library is the Lua 5.5.0 tarball from lua.org, not a git repository at a commit, its harness is OSS-Fuzz's example of luzer, and the release did not build it.
  * JavaScript: held. The same driver change as Lua's; no JavaScript toolchain image on this toolchain; and two questions to decide: whether to publish the third-party npm trees that the builds pin (one is AGPL), and where their source mirror lives.
  * Ruby (2 projects): not ported. Both are over the size cap, and the release's toolchain image for Ruby is not reproducible (one tag, two image ids).
* **JVM and R** wait: JVM until a native-image build is byte-reproducible; R until the decision on its sanitizer builds.
* **docs/faq.md** has questions marked "To be confirmed": rechecks before a report and findings in dependencies, and where findings are kept.
* **Asserts compiled out in CMake builds.** A library built with CMake's `Release` build type, as cjson's and many ported builds are, is compiled with `NDEBUG`, so its `assert`s are compiled out and a failed one is not caught, where OSS-Fuzz's build of the same fuzz target often keeps them. Building it otherwise would change the bytes of the release's binaries, so this is a known exception to what the statements catch ([docs/what-gets-proven.md](docs/what-gets-proven.md)) until the next toolchain vintage ([docs/build-contract.md](docs/build-contract.md#toolchains)).
* **The proofs repository** (oss-verify-proofs) does not exist yet. The lock is to be written from `tools/check`'s manifest, and the triage comment's "Proofs index" row assumes the index layout of oss-fuzz-theorems.
* **Placeholders** to replace before this repository opens: the [terms](https://theorem.dev/oss-verify/terms/) URL and the contact in [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).
* **Images to publish before this repository opens**, each by the digest that infra/toolchains.tsv names: the C and C++ toolchain image, and the release's Rust, Python and Go toolchain images (`ghcr.io/theorem-labs/oss-fuzz-theorems-toolchain-rust@sha256:ad8a4572…`, `ghcr.io/theorem-labs/oss-fuzz-theorems-toolchain-python@sha256:912c88bf…`, `ghcr.io/theorem-labs/oss-fuzz-theorems-toolchain-go@sha256:bb18d922…`). All four are private today, so `tools/check` works only on a machine that has them.

## Seeded projects

`tools/seed.py` writes a `project.yaml` from the oss-fuzz-theorems 2026.10 release's metadata, only where that metadata says everything needed. A seeded project says `primary_contact: n/a` until its maintainers adopt it ([CONTRIBUTING.md](CONTRIBUTING.md)). It is published only because it has no findings: a finding for it is sent nowhere unless someone hands it over by hand, and nothing is sent automatically ([docs/what-gets-proven.md](docs/what-gets-proven.md#findings)). Its `Dockerfile` and `build.sh` are added only once `tools/check` has built them and they reproduce the release's binaries.

### Draft branches

One for each of the other 302 C and C++ projects `tools/seed.py` can seed: `draft-generic-oss-fuzz-<name>` is `main` plus that project, regenerated with `tools/seed.py --branch` when `main` changes. 301 have build files that reproduce the release's binaries (md4c's and wasm3's written by hand, the others ported), kept on `main` in `tools/seeds/<name>/`. varnish has only a `project.yaml`, since its port fails (above), as its commit message says.

One for each of the 31 Rust projects that the release's Rust build built but did not publish ([tools/seeds/languages.tsv](tools/seeds/languages.tsv)): OSS-Fuzz's hyperium and unicode-rs are two projects each here, one for each repository (h2 and http; unicode-normalization and unicode-segmentation). Their build files are ported from that build, with the two package names renamed (above). tools/seeds/builds.tsv and each commit message say how each fared: each builds twice with identical bytes, and has no release binary to compare.

One for each of the 31 Python projects that the release's Python build built but did not publish ([tools/seeds/languages.tsv](tools/seeds/languages.tsv)). Their build files are ported from that build. tools/seeds/builds.tsv and each commit message say how each fared: mdurl and idna reproduce the release's binaries, and the 29 others build twice with identical bytes and have no release binary to compare.

One for each of the 22 Go projects that the release's Go build built but did not publish ([tools/seeds/languages.tsv](tools/seeds/languages.tsv)). Their build files are ported from that build, and each reproduces the release's binaries, as tools/seeds/builds.tsv and each commit message say.

### Everything else

[docs/seeded-projects.tsv](docs/seeded-projects.tsv) says, for each of the release's 1,381 projects, whether it can be seeded and why not, and for each one that can, how its ported build fared. 394 of them can be seeded, as 396 projects here: 312 in C or C++, 31 in Python, 29 in Rust, of which hyperium and unicode-rs are two projects each, and 22 in Go. Of the rest, 958 were not built by the release (699 in a language other than C or C++, 120 too large, 78 not built yet, 32 with no harness, 17 held, 6 excluded, 3 needing model support, 3 with no compiler), 25 have no harness whose build leaves the library's own source alone, and 4 have no full commit recorded.
